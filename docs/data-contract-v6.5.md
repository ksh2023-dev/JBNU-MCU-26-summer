## 0. 대전제

### 0-1. 할루시네이션 방지 4원칙

이 프로젝트는 없는 값을 지어내는 순간 서비스가 실패합니다. 아래 4원칙은 백엔드가 응답을 만들 때, 그리고 AI로 데이터를 수집·정리·생성할 때 반드시 지킵니다.

1. **모든 API 응답 논문에는 `pmid` 또는 `kciId` 중 최소 하나가 필수.** 둘 다 `null`인 논문은 응답에 넣지 않는다. *(v6.4에서 확장된 규칙을 v6.5에서도 그대로 유지)*
   - **실제 출처에서 확인된 식별자만 사용한다.** 존재하지 않는 PMID·KCI article ID를 생성하지 않으며, 형태만 그럴듯한 값을 지어내지 않는다
   - 두 식별자는 **함께 존재할 수 있다.** PubMed에도 등재된 국내 논문은 `pmid`와 `kciId`를 모두 가지며, **API 응답에도 둘 다 담는다** (1-2)
   - **두 필드는 각각 nullable이다** (`string | null`). 필수인 것은 **특정 식별자가 아니라 "둘 중 최소 하나"** 이므로, **KCI-only 논문의 `pmid = null`은 정상 상태다** (1-2)
2. 값이 없는 필드는 지어내지 말고 `null`로 보낸다. (화면 표시 문구 "정보 없음"은 프론트가 붙인다. 빈칸으로 두지 않는다)
3. **검색어가 있는 경우**, `matchScore`가 임계값(`minScore`) 미만인 교수는 결과에서 제외한다. 억지로 채우지 않는다.
   - 빈 검색어(`query: ""`) 전체 조회에서는 `matchScore`가 `null`이라 임계값 비교가 불가능하므로 `minScore`를 적용하지 않는다. (2장 API ① browse 정책)
4. 응답에 데이터 수집 기준일(`collectedAt`)을 담는다. 교수명·이메일·논문 값은 DB 원본 그대로, 재작성 금지.

AI로 데이터를 만들 때 프롬프트 맨 앞에 붙일 규칙 (그대로 복사):

```
너는 <교수_데이터> 안의 값만 사용한다.
- 데이터에 없는 교수·논문·연구실·이메일·ORCID를 절대 생성하지 마라.
- 값이 없으면 지어내지 말고 null로 두어라.
- 논문은 pmid 또는 kciId가 있는 것만 포함하라. 둘 다 없으면 그 논문은 빼라.
- pmid·kciId는 원본 값을 그대로 쓰고, 없는 쪽은 null로 두어라. 식별자를 새로 만들어내지 마라.
- 제목·학술지·연도는 원본 그대로 두어라.
- 근거가 부족하면 "제공된 데이터로는 확인할 수 없습니다"라고만 답하라.
```

## 1. 공통 데이터 객체

### 1-1. 교수 카드 (검색 결과 · featured 1건)

```json
{
  "id": "P-012",
  "name": "김민수",
  "profileImageUrl": null,
  "professorType": "임상의학",
  "department": "순환기내과",
  "specialties": ["심장영상", "심부전"],
  "keywords": ["cardiac imaging", "heart failure", "biomarker"],
  "matchScore": 0.87
}
```

- 같은 모양을 교수 검색 결과와 featured(최근 연구 활동 교수)에서 공통으로 사용
- `id` — 내부 식별자, 화면에는 표시하지 않음. **한 번 부여되면 변경되지 않는다** (프론트 찜이 localStorage에 id로 저장되므로)
- `profileImageUrl` — 없으면 `null` (프론트가 이니셜 아바타로 대체)
- `professorType` — 교수 구분 필터값. 값 집합: `기초의학 | 임상의학 | 의학교육학 | 인문사회의학`
- `department` — 소속교실 또는 진료과. **분과·겸직이 병기될 수 있다** (예: `내과학교실(소화기)`, `예방의학교실 · 가정의학교실`)
- `specialties` — 전문 분야. 여러 개를 담는 배열(`[ ]`). 값이 하나여도 배열로 보냄. 없으면 빈 배열 `[]`
- `keywords` — **응답에는 전체 배열을 담고, 카드 화면에는 앞 4개까지 표시한다 (v6.5)**. 아래 참고
- `matchScore` — **`number | null`** (아래 참고)
- 찜 여부·이메일은 카드에 넣지 않음 — 찜 여부는 프론트가 `id`를 localStorage와 대조해 판단, 이메일은 상세에서만 표시

#### `keywords` — 데이터 선택 규칙 + 화면 표시 정책 (v6.5 확정)

**데이터 선택 규칙 — v6.5 확정 (v6.4의 "MeSH 기반 영문 키워드"를 대체)**

`keywords`는 **서비스 검색과 화면 표시에 사용하는 최종 키워드 배열**이며, 아래 우선순위로 만들어진다.

| 순위 | 조건 | 결과 |
| --- | --- | --- |
| 1 | `meshTerms`가 **non-empty** | `keywords = meshTerms` |
| 2 | `meshTerms`가 `[]`이고, **`kciKeywords.en`이 non-empty** | `keywords = kciKeywords.en` |
| 3 | `meshTerms`와 `kciKeywords.en`이 **모두 `[]`** | `keywords = []` |

```text
meshTerms non-empty                        → meshTerms 사용
meshTerms [] + kciKeywords.en non-empty    → kciKeywords.en 사용
meshTerms [] + kciKeywords.en []           → keywords: []
```

- **이 세 필드는 항상 존재하는 배열이므로**(아래 배열 규칙), 판정은 **`[]`인지 아닌지**만 보면 된다
- **`kciKeywords.ko`와 `keywordsKo`는 이 fallback에 사용하지 않는다.** 두 필드는 한글 검색을 위한 내부 데이터이며, 최종 표시용 `keywords`는 영문 배열이다. **`keywordsKo`는 이 fallback이 끝난 뒤 최종 `keywords`를 한글화해 만드는 값**이므로 입력이 아니라 결과다 (아래)
- **최종 `keywords`는 영문 배열이다 (v6.5 확정).** MeSH를 쓰면 영문 MeSH 용어이고(예: `"Heart Failure"`), MeSH가 없어 KCI로 fallback할 때에도 **KCI가 제공한 영문 keyword(`kciKeywords.en`)를 사용한다**. 한글 원본은 `keywords`에 넣지 않고 내부 필드에 보존한다 (아래)
- **백엔드는 최종 `keywords` 전체 배열을 응답에 담는다.** 개수를 잘라서 보내지 않는다
- **화면 표시에는 `keywords`만 사용한다.** 화면에 몇 개를 보여주는지는 아래 화면 표시 정책을 따른다
- **검색 매칭에는 `keywords` 외에 내부 keyword 필드까지 모두 사용한다** — keyword 계열 **전체의 합집합**이며, 아래 `검색에 사용하는 keyword 계열` 참고. 프론트는 이 내부 구조를 알 필요가 없다
- 한글 검색어와 영문 `keywords` 사이의 간극은 내부 한글 keyword 필드와 5장의 **검색어 별칭 규칙**으로 해결한다 — `keywords` 자체를 바꾸는 것이 아니다

**내부 keyword 필드 — `professors.json`에 보존한다 (v6.5 확정)**

`professors.json`의 교수 데이터에는 아래 네 필드를 보존한다. **이 중 API 응답에 나가는 것은 `keywords` 하나뿐이다.**

구조 예 (값은 **구조 설명용 예시**이며 특정 교수의 실제 데이터가 아니다):

```json
{
  "keywords": ["Heart Failure", "Cardiac Imaging"],
  "meshTerms": ["Heart Failure", "Cardiac Imaging"],
  "keywordsKo": ["심부전", "심장 영상"],
  "kciKeywords": {
    "ko": ["심부전", "심장영상"],
    "en": ["Heart Failure", "Cardiac Imaging"]
  }
}
```

| 필드 | 타입 | 값이 없을 때 | API 응답 | 역할 |
| --- | --- | --- | --- | --- |
| `keywords` | `string[]` | `[]` | **포함** | API 응답·화면 표시용 **최종 영문** keyword 배열. 위 우선순위로 만든다 |
| `meshTerms` | `string[]` | `[]` | **미포함 (내부)** | PubMed/MeSH에서 수집한 **원본 영문** terms |
| `keywordsKo` | `string[]` | `[]` | **미포함 (내부)** | **최종 `keywords`를 한글화한 결과**. 한글 검색을 위한 **검색용 내부 필드**다 |
| `kciKeywords` | `{ "ko": string[], "en": string[] }` | 각 배열이 `[]` | **미포함 (내부)** | KCI가 제공한 **원본** keyword. 한글과 영문을 **출처별로 구분해** 보존한다 |

- **`kciKeywords`는 단순 문자열 배열이 아니라 `{ ko, en }` 구조다.** `kciKeywords.ko`는 KCI가 제공한 원본 한글 keyword, `kciKeywords.en`은 KCI가 제공한 원본 영문 keyword다
**`keywordsKo` — 최종 `keywords`를 한글화한 검색용 필드 (v6.5 확정)**

- **번역 입력은 `meshTerms`가 아니라 fallback 선택이 끝난 최종 `keywords`다.** 관계는 다음과 같다.

```text
원본 수집(meshTerms · kciKeywords) → 최종 영문 keywords 선택 → keywordsKo 생성(한글화)
```

- 입력: **최종 `keywords`** / 출력: **`keywordsKo`** / 용도: **내부 한글 검색** / **API 미응답**
- **`keywordsKo`는 API 응답에 포함하지 않고 화면에도 직접 표시하지 않는다.** 검색을 위한 내부 필드다
- 한글화의 **구체적인 기계번역 모델·번역 API·스크립트 구현 방식은 이 데이터 계약의 범위 밖이다** — 이 계약이 정하는 것은 **입력·출력·용도·API 미응답**까지다

> **왜 `meshTerms`가 아니라 `keywords`를 번역하는가 (v6.5 변경 — 기존 `meshTermsKo` 방식을 대체)**
>
> 종전 방식(`meshTerms`만 한글화)은 **MeSH가 있는 교수에게만 한글 검색 데이터를 만들 수 있었다.** MeSH가 없는 교수는 `kciKeywords.en`이 최종 `keywords`가 되는데, 그 경우 한글 검색 대응값이 생기지 않는다.
>
> **최종 `keywords` 자체를 한글화하면 출처가 MeSH든 KCI 영문이든 관계없이 동일한 흐름으로 한글 검색 데이터를 만들 수 있고**, 번역 입력도 `keywords` 하나로 통일되어 데이터 파이프라인이 단순해진다.
>
> `keywordsKo`는 **KCI 원본 한글 keyword를 대체하는 필드가 아니다.** KCI 원본 한글은 제공 비율이 낮아 `kciKeywords.ko`만으로는 한글 검색 커버리지를 확보할 수 없으므로(아래 KCI 수집 결과 참고), `keywordsKo`는 **커버리지를 안정적으로 확보하기 위한 별도의 번역 필드**다.

**`keywordsKo`와 `kciKeywords.ko`의 차이 — 둘 다 한글이지만 성격이 다르다**

| 필드 | 성격 | 출처 |
| --- | --- | --- |
| `keywordsKo` | **번역·가공 데이터** | 최종 영문 `keywords`를 한글화한 결과. **원문 출처 keyword가 아니다** |
| `kciKeywords.ko` | **원본 데이터** | KCI가 직접 제공한 원본 한글 keyword. **번역 결과가 아니다** |

- **두 배열을 하나의 내부 필드로 합치지 않는다.** 검색에는 둘 다 활용하지만, **데이터 출처를 추적할 수 있도록 별도 필드로 보존한다**

**배열형 keyword 필드는 항상 배열이다 — 빈 값은 `[]` (v6.5 확정)**

값의 부재를 표현하는 이 계약의 기본 원칙은 다음과 같다 (4장 참고).

| 값이 없을 때 | 표현 |
| --- | --- |
| **값의 부재가 허용되는(nullable) 스칼라 필드** (`email` · `homepageUrl` · `profileImageUrl` · `matchScore` 등) | **`null`** |
| **배열 필드** (`keywords` · `keywordsKo` · `meshTerms` · `kciKeywords.ko` · `kciKeywords.en` · `specialties` · `papers` 등) | **`[]`** |

`id` · `name` 처럼 **값이 반드시 있어야 하는 스칼라 필드는 `null`을 허용하지 않는다** — 위 `null` 규칙은 4장 표에 nullable로 명시된 필드에만 적용된다.

위 keyword 관련 배열 다섯 개(`keywords` · `keywordsKo` · `meshTerms` · `kciKeywords.ko` · `kciKeywords.en`)에는 **예외 없이** 다음이 적용된다.

- **항상 필드가 존재한다.** 값이 없다는 이유로 필드를 **생략하지 않는다**
- **항상 배열이다.** 값이 없어도 타입이 바뀌지 않는다
- **값이 없으면 `[]`** 를 쓴다. **`null`을 쓰지 않는다**
- **`kciKeywords` 객체 자체도 항상 존재하고, 그 안의 `ko`·`en`도 항상 존재한다.** 둘 다 타입은 `string[]`이며, 값이 없으면 `[]`다. 객체를 `null`로 두거나 `kciKeywords`·`ko`·`en` 중 어느 하나라도 생략하지 않는다 — 한쪽 언어의 keyword만 있어도 나머지 한쪽을 `[]`로 둔다

한글 keyword만 있는 경우:

```json
{
  "kciKeywords": {
    "ko": ["심부전", "심장영상"],
    "en": []
  }
}
```

영문 keyword만 있는 경우:

```json
{
  "kciKeywords": {
    "ko": [],
    "en": ["Heart Failure", "Cardiac Imaging"]
  }
}
```

keyword를 하나도 확보하지 못한 교수의 내부 구조 (**필드는 모두 존재하고 값만 `[]`**):

```json
{
  "keywords": [],
  "keywordsKo": [],
  "meshTerms": [],
  "kciKeywords": {
    "ko": [],
    "en": []
  }
}
```

> **참고 — KCI keyword 수집 완료 (v6.5) · `[]`의 의미**
>
> KCI keyword 수집은 **완료되었다.** 따라서 `kciKeywords.ko` · `kciKeywords.en`의 `[]`는 **"아직 수집 전"이라는 뜻이 아니라, 그 언어의 KCI 원본 keyword를 확보하지 못했다는 뜻**이다.
>
> - KCI 원본에서 그 언어의 keyword를 **확보한 경우 → 배열에 저장**
> - KCI 원본이 그 언어의 keyword를 **제공하지 않는 경우 → `[]`**
>
> **수집이 정상적으로 완료된 뒤에도 `kciKeywords.ko = []`인 레코드가 다수 존재하는 것이 정상이다.** 한국어 논문이라 하더라도 KCI가 한글 keyword를 반드시 제공하지는 않기 때문이다. **"수집이 끝나면 `kciKeywords.ko`가 전부 채워질 것"이라고 기대하면 안 된다.**
>
> **`kciKeywords.en`도 모든 레코드에서 값이 존재한다고 계약하지 않는다.** 확보하지 못하면 마찬가지로 `[]`다.
>
> *현 데이터셋 실측(참고값 · 계약 보장값 아님)*: `kciKeywords.en`은 약 **92.3%**, `kciKeywords.ko`는 약 **20.3%**에서 값이 확보되었다. 한국어 논문 1,136편 중 687편이 **영문 keyword만** 제공하는 사례도 확인되었다. **이 수치는 현재 수집 결과를 설명하는 시점성 참고값이며, 향후 데이터가 같은 비율을 유지해야 한다는 계약 조건이 아니다.**
>
> 계약상 유효한 규칙은 **① 필드는 항상 존재 ② 타입은 항상 `string[]` ③ 원본 값이 없으면 `[]`** 세 가지다 (위 배열 규칙).
>
> 한편 KCI 원본 한글 keyword의 제공 비율이 낮아 **`kciKeywords.ko`만으로는 한글 검색을 보완할 수 없으므로**, 한글 검색 커버리지는 최종 `keywords`를 한글화한 **`keywordsKo`** 로 확보한다 (위 참고).
>
> 이 사항은 **API 응답 스키마 변경을 의미하지 않는다.** `kciKeywords`는 종전대로 내부 필드이며 응답에 나가지 않고, **프론트는 `kciKeywords`를 직접 사용하지 않는다.**

**검색에 사용하는 keyword 계열 — keyword 계열 전체의 합집합 (v6.5 확정)**

**표시용 keyword 선택과 검색용 keyword 범위는 목적이 다르므로 분리한다.**

- `keywords` — 화면·API에 **표시할 대표 영문 keyword 배열**. 위 우선순위 규칙으로 **하나를 골라** 만든다
- **검색** — 내부에 보존된 **keyword 계열 전체**를 활용한다. 고르지 않고 **전부 합친다**

```text
검색 대상 keyword 계열
  = keywords ∪ keywordsKo ∪ meshTerms ∪ kciKeywords.ko ∪ kciKeywords.en
    (합친 뒤 중복 제거)
```

| 필드 | 검색에서의 역할 |
| --- | --- |
| `keywords` | 화면·API용 **대표 영문** keyword 매칭 |
| `keywordsKo` | 최종 `keywords`의 **한글 검색 대응값** — 출처가 MeSH든 KCI 영문이든 동일하게 한글 검색을 지원한다 |
| `meshTerms` | PubMed/MeSH **원본 영문** terms 매칭 |
| `kciKeywords.ko` | KCI가 제공한 **원본 한글** keyword 검색 지원 |
| `kciKeywords.en` | KCI가 제공한 **원본 영문** keyword 검색 지원 |

- **다섯 필드를 모두 합친 뒤 중복을 제거해서** 검색에 쓴다
- **왜 합집합인가** — 표시용 규칙은 `meshTerms`와 `kciKeywords.en` 중 **하나만** 고른다. MeSH가 있는 교수는 `keywords = meshTerms`가 되어, 검색 범위를 표시용 `keywords` 기준으로 잡으면 **그 교수의 `kciKeywords.en`이 검색에서 빠진다.** 두 범위를 분리하면 이 누락이 생기지 않는다
- **표시용 `keywords` 선택 규칙이 나중에 바뀌더라도 검색 가능 범위가 불필요하게 줄어들지 않는다.** 검색은 표시 규칙의 결과가 아니라 보존된 원본 전체를 본다
- **중복 제거의 세부 방식(대소문자·띄어쓰기·문장부호 정규화, stemming, 형태소 분석, 동의어 병합, 대표값 선택 등)은 이 계약에서 새로 정하지 않는다.** 이 계약이 정하는 것은 **"합친 뒤 중복을 제거한다"** 까지다. 한글 검색어와 영문 값 사이의 별칭 처리는 여전히 별도의 미확정 항목이다 (5장 미확정 3번)
- **프론트는 이 내부 검색 구조를 알 필요가 없다.** 프론트가 받는 것은 `keywords` 하나뿐이다
- **검색에 다섯 필드를 쓰더라도 API 응답 필드에 `keywordsKo`·`meshTerms`·`kciKeywords`(및 `.ko`/`.en`)를 추가하지 않는다.** 이번 결정은 **프론트 ↔ 백엔드 API 응답 스키마 변경이 아니다**

**KCI keywords 번역 정책 (v6.5 확정)**

- KCI는 한글·영문 keywords를 함께 제공하므로 **서비스에서 KCI keyword에 대한 별도의 AI·KMLE 번역 과정을 두지 않는다**
- KCI에서 받은 keyword 원본은 `kciKeywords.ko` / `kciKeywords.en`에 **출처 그대로** 보존한다
- MeSH가 없는 경우 **KCI가 제공한 영문 keyword(`kciKeywords.en`)를 별도 번역 없이 fallback으로 활용한다**
- **프론트는 keyword를 번역하거나 새로 생성하지 않는다** (원칙 2). 받은 `keywords` 배열을 그대로 표시한다

**화면 표시 정책 — v6.5 신설 (v6.4의 "화면 미표시"를 대체)**

| 화면 | 표시 |
| --- | --- |
| 교수 카드 — HomePage · SearchResultPage · FavoritesPage | 응답 배열의 **순서를 유지한 채 앞 4개까지** |
| 교수 카드에서 4개를 초과할 때 | 나머지 개수를 **`+N`** 으로 표시 (예: 총 7개 → 앞 4개 + `+3`) |
| 교수 상세 — ProfessorDetailPage | **전체 표시** (자르지 않는다) |
| `keywords: []` | 카드·상세 **모두 해당 키워드 영역을 표시하지 않는다** |

- 위 세 화면은 같은 `ProfessorCard` 컴포넌트를 쓴다. **표시 개수 제한은 `ProfessorCard` 한 곳에서만 한다** — 페이지가 미리 잘라서 넘기면 같은 교수 데이터가 화면마다 다르게 보이고, `+N`도 이미 잘린 배열 길이로 계산되어 실제 개수와 어긋난다
- **`keywords` 배열의 순서는 백엔드가 응답으로 제공한 순서를 그대로 사용한다.** 프론트는 중요도·관련도를 재계산하거나 배열을 재정렬하지 않고, 그 순서 위에서 "표시 개수"만 앞에서 자른다
- 백엔드/조립기가 `keywords` 배열을 **어떤 순서로 생성할지는 아직 확정되지 않았다** → 5장 미확정 6번. **순서를 결정할 책임은 프론트가 아니라 백엔드·데이터 조립 단계에 있으며**, 프론트 구현은 이 결정을 기다릴 필요 없이 받은 순서를 그대로 쓰면 된다 (**어느 출처에서 값을 가져올지**는 위 데이터 선택 규칙으로 이미 확정되었다 — 미확정인 것은 그렇게 만들어진 배열의 **순서**뿐이다)

> 카드 앞 4개 + `+N`, 상세 전체 표시라는 v6.5 `keywords` 화면 정책은 이 내용으로 완결된다.

#### `matchScore` — `number | null` (v6.2 확정, 변경 없음)

| 상황 | 값 |
| --- | --- |
| 검색어가 있는 검색 결과 (`query`에 값 있음) | `0 ~ 1` 사이 실수 (관련도 점수) |
| 빈 검색어 전체 조회 (`query: ""`) | `null` |
| featured 교수 카드 (API ③) | `null` |

- **`matchScore: null`은 오류가 아니라 정상 상태다.** 검색어가 없어 관련도를 계산하지 않았다는 뜻이다 (원칙 2·3)
- 프론트는 `matchScore`가 항상 숫자라고 가정하지 않는다. 현재 카드 UI는 점수를 표시하지 않는다

### 1-2. 교수 상세

```json
{
  "id": "P-012",
  "name": "김민수",
  "profileImageUrl": null,
  "professorType": "임상의학",
  "department": "순환기내과",
  "specialties": ["심장영상", "심부전"],
  "keywords": ["cardiac imaging", "heart failure", "biomarker"],
  "email": "kim@jbnu.ac.kr",
  "homepageUrl": null,
  "papers": [
    { "title": "Prognostic value of cardiac MRI ...", "journal": "JACC", "year": 2022,
      "pmid": "35123456", "kciId": null },
    { "title": "국내 심부전 환자의 예후 인자 분석", "journal": "대한내과학회지", "year": 2021,
      "pmid": null, "kciId": "ART002712345" }
  ]
}
```

- 위쪽 `id` ~ `keywords`는 카드(1-1)와 동일한 칸 이름을 사용
- `keywords` — 응답은 카드와 같은 **최종 전체 배열**(MeSH 우선 → 없으면 KCI → 둘 다 없으면 `[]` · 1-1)이고, 상세 화면에서는 **자르지 않고 전체를 표시한다 (v6.5)**. 빈 배열 `[]`이면 키워드 영역 자체를 표시하지 않는다
- **`labName` 필드는 v6.4에서 삭제되었다.** 수집 가능한 출처가 없어 전원 `null`이었고, 프론트 화면에서도 제거하기로 확정(2026-08-16 회의)
- `homepageUrl` · `email` — 데이터 없으면 `null`
- `homepageUrl` — 임상 교수는 병원 프로필, 기초 교수는 학교 홈페이지 URL
- `papers` — 최신순 1편 + 인용수 상위 2편 = 3편 (7/23 회의 결정). 논문이 없으면 빈 배열 `[]`. **최신 1편이 인용수 상위 논문과 겹칠 때의 중복 처리 규칙은 미확정이다** → 5장 미확정 4번

#### `papers`의 논문 식별자 `pmid` / `kciId` (v6.4 도입 · v6.5에서도 유지)

**API 응답의 논문 식별자는 `pmid`와 `kciId` 두 필드다.** 각 논문은 **둘 중 최소 하나를 반드시 가지며**, 둘 다 `null`인 논문은 응답에 넣지 않는다 (원칙 1).

| 필드 | 타입 | 의미 | 값이 없을 때 |
| --- | --- | --- | --- |
| `pmid` | **`string \| null`** | PubMed 논문 고유번호 (PMID) | `null` |
| `kciId` | **`string \| null`** | KCI(한국학술지인용색인) 논문 고유 ID (`ART...` 형식) | `null` |

- **두 필드 모두 nullable이다.** `pmid`는 PubMed 식별자가 없는 논문에서, `kciId`는 KCI 식별자가 없는 논문에서 각각 `null`이 된다
- **논문 단위의 필수 조건은 `pmid` 자체가 아니라 `pmid != null || kciId != null` 이다.** 즉 필수인 것은 **특정 식별자**가 아니라 **논문을 식별할 수 있다는 조건**이다
- **둘 중 최소 하나는 반드시 존재한다.** 둘 다 `null`인 논문은 계약 위반이며 `papers[]`·응답에 넣지 않는다 (원칙 1)
- **둘 다 존재할 수 있다.** 국제 학술지 논문은 대개 `pmid`만, 국내 학술지 논문은 대개 `kciId`만 가지지만, **국내 학술지 중 PubMed에도 등재된 논문은 `pmid`와 `kciId`를 모두 가진다** (아래 중복 처리 규칙)
- **두 값 모두 화면에 직접 표시하지 않는다. 원문 링크 생성에만 사용한다** (3장 참고)
- **논문 URL 문자열은 데이터·API 응답에 저장하지 않는다 (v6.5).** `papers`에는 식별자만 담고, 주소는 프론트가 두 식별자로 조립한다 (3장)

**식별자 조합 판정 — 네 경우 (v6.5 명시)**

| # | `pmid` | `kciId` | 판정 |
| --- | --- | --- | --- |
| A. PubMed-only | 존재 | `null` | **정상** |
| B. **KCI-only** | **`null`** | 존재 | **정상** |
| C. PubMed + KCI | 존재 | 존재 | **정상** — 두 값을 모두 보존해 응답에 담는다 |
| D. 식별자 없음 | `null` | `null` | **계약 위반** — `papers[]`에 포함하지 않는다 (원칙 1) |

**KCI-only 논문(`pmid = null`)은 계약상 정상 상태다**

- **KCI-only 논문은 계약이 정식으로 지원하는 데이터다.** `pmid = null` · `kciId != null`인 레코드는 **오류가 아니다**
- **`pmid`가 `null`이라는 이유만으로 논문 데이터 적재나 API 응답이 실패해서는 안 된다.** 백엔드의 데이터 모델·검증 로직은 KCI-only 논문을 정상적으로 처리할 수 있어야 한다
- **"모든 논문에 `pmid`가 필수"는 이 계약의 규칙이 아니다.** 계약의 규칙은 **"모든 논문에 `pmid` 또는 `kciId` 중 최소 하나가 필수"** 다
- KCI-only 논문도 `kciId`로 원문 링크를 정상적으로 만들 수 있다 (3장)

> **`latestPaper`의 `pmid` 요구 조건과 혼동하지 않는다.** `latestPaper`는 **PubMed-only 내부 필드**라 유효한 `pmid`(와 완전한 `YYYY-MM-DD` `publishedAt`)를 요구하지만(2장 API ③), 그것은 **featured 선정 후보 조건**이다. **일반 `papers[]`에는 그 조건을 적용하지 않는다** — `papers`에는 KCI-only 논문이 그대로 포함된다.

> **⚠️ 구현 주의사항 — 현재 백엔드 스키마와 계약의 차이 (구현 TODO)**
>
> 계약상 `papers[].pmid`는 **nullable**이고 KCI-only 논문은 **정상 데이터**다. 그러나 **현재 백엔드 스키마가 `papers[].pmid`를 필수 문자열로 처리하고 있다면 계약과 불일치**하며, `pmid = null`인 KCI-only 논문이 `professors.json`에 하나라도 포함되면 **전체 데이터 적재가 실패할 수 있다.**
>
> **이는 정책이 미정이라는 뜻이 아니다.** 계약은 위와 같이 이미 확정되어 있고, **계약 병합 후 백엔드 스키마·검증 로직을 계약에 맞춰 수정해야 하는 구현 항목**이다.
>
> 백엔드 구현이 만족해야 하는 조건:
>
> - `pmid`를 **nullable**로 처리할 수 있어야 한다
> - `kciId`를 **nullable**로 처리할 수 있어야 하며, **필드 자체가 스키마에 존재해야 한다**
> - 단, **둘 다 `null`인 경우는 허용하지 않는다**
> - 따라서 논문 검증은 **각 필드의 개별 required 여부가 아니라 "`pmid`/`kciId` 중 최소 하나 존재" 조건**을 검사해야 한다 (위 판정 표 A·B·C 통과, D 실패)
> - **KCI-only 논문이 포함되어도 `professors.json` 전체 적재가 실패해서는 안 된다**
>
> 구체적인 스키마 코드 형태는 이 계약에서 설계하지 않는다 — 위 조건을 만족하면 된다.

| --- | --- |

#### PubMed · KCI 중복 논문 처리 (v6.4 신설 · 적용 범위는 v6.5에서 명시)

일부 국내 학술지(J Korean Med Sci, Korean J Intern Med 등)는 PubMed에도 등재되어 있어 같은 논문이 양쪽에서 수집될 수 있다. 파이프라인은 아래 규칙으로 하나의 논문으로 합친다.

> **이 절은 `동일한 교수`에 대해 같은 논문이 두 출처(PubMed · KCI)에서 수집된 경우의 병합 규칙이다.** 서로 다른 교수 레코드 사이의 동일 논문은 병합 대상이 아니며, 바로 아래 `동일 논문의 복수 교수 귀속`을 따른다 (v6.5).

**동일 논문 판별 (우선순위 순)**

1. **DOI 일치** — 양쪽 모두 DOI를 제공하므로 최우선 기준
2. DOI가 없으면 **정규화한 제목 + 발행연도** 일치 (대소문자·공백·구두점 무시, 영문 제목 우선 비교)
3. 그래도 판별이 어려우면 **별개 논문으로 두고 검수 목록에 기록한다.** 임의로 합치지 않는다 (원칙 2)

**병합 정책**

- 중복 판정 시 레코드를 **하나로 합치고, `pmid`와 `kciId`를 모두 보존한다**
- **병합된 논문은 API 응답에서도 `pmid`와 `kciId`를 둘 다 제공한다.** 식별자를 하나만 남기도록 고르지 않는다 (1-2 식별자 설명)
- **동일 교수의 `papers` 배열에 같은 논문을 두 번 저장하지 않는다.** 병합 결과는 한 건이다
- 대표 논문 3편 선정의 인용수 기준: **국제 인용수(OpenAlex) 우선, 없으면 KCI 피인용수**
- 초록은 영문(PubMed)과 한글(KCI)을 내부 데이터로 함께 보존한다 (검색 매칭에 활용)
- **키워드도 출처별로 분리 보존한다 (v6.5)** — PubMed/MeSH 원본은 `meshTerms`, KCI 원본은 `kciKeywords.ko` / `kciKeywords.en`에 담고, 최종 `keywords`는 **MeSH 우선 → 없으면 `kciKeywords.en`** 규칙으로 만든 뒤 그 결과를 한글화해 `keywordsKo`에 담는다 (1-1). `keywordsKo`·`meshTerms`·`kciKeywords`는 내부 데이터 전용이며 응답에 나가지 않는다

#### 동일 논문의 복수 교수 귀속 (v6.5 신설)

동일한 논문에 **본 서비스 대상 교수가 여러 명 공저자로 참여한 경우, 해당 논문은 각 교수의 논문으로 모두 인정한다.**

바로 위의 중복 병합 규칙과 적용 범위가 다르므로, 아래 두 가지를 반드시 구분한다.

| 구분 | 상황 | 처리 |
| --- | --- | --- |
| **A. 동일 교수 내부 중복** | 같은 교수의 같은 논문이 PubMed와 KCI에서 각각 수집됨 | **하나로 병합한다.** 위 `PubMed · KCI 중복 논문 처리`의 판정 규칙(DOI → 정규화 제목+연도 → 검수)을 그대로 적용하고, 병합된 한 건에 `pmid`와 `kciId`를 모두 보존해 응답에도 둘 다 담는다. **동일 교수의 `papers` 배열 안에 같은 논문을 두 번 저장하지 않는다** |
| **B. 서로 다른 교수 간 동일 논문** | 교수 A와 교수 B가 같은 논문의 공저자 | **각 교수에게 모두 귀속한다.** 교수 레코드 간에는 **동일한 `pmid`·`kciId`가 존재할 수 있으며**, **교수 간 중복 제거를 수행하지 않는다** |

**B — 교수 간 동일 식별자 허용**

- 서로 다른 교수 레코드 간 **동일한 `pmid`의 중복을 허용한다**
- 서로 다른 교수 레코드 간 **동일한 `kciId`의 중복을 허용한다**
- 동일한 논문이 교수 A와 교수 B의 `papers`에 각각 존재할 수 있다
- 이는 **데이터 중복 오류가 아니라 정상적인 공저자 관계**다
- 교수 간 **전역(global) 기준으로 `pmid`·`kciId`를 unique하게 만들거나, 하나의 교수에게만 논문을 귀속해서는 안 된다**
- 검증된 공저 논문이라면 **동일한 식별자가 여러 교수 레코드에 반복되는 것이 정상이다**

예 — 아래 두 교수 레코드는 정상적인 데이터다.

교수 A:

```json
{
  "papers": [
    { "title": "Example Paper", "pmid": "12345678", "kciId": null }
  ]
}
```

교수 B:

```json
{
  "papers": [
    { "title": "Example Paper", "pmid": "12345678", "kciId": null }
  ]
}
```

**교수 귀속 시 저자 검증 필수**

- 논문을 교수에게 귀속할 때에는 **해당 교수가 실제 그 논문의 저자임이 검증되어야 한다**
- **동일한 `pmid`·`kciId`가 다른 교수 레코드에 이미 존재한다는 사실만으로 해당 논문을 새로운 교수에게 귀속해서는 안 된다**
- 교수별 논문 귀속은 **해당 교수가 실제 저자임이 확인된 경우에만** 인정한다
- 즉 위 `동일 식별자 중복 허용`은 **검증된 공저자 관계를 표현하기 위한 규칙**이지, 동일한 `pmid`·`kciId`를 근거로 **논문을 다른 교수에게 자동 복제하는 규칙이 아니다**
- 저자임을 확인할 근거가 부족하면 **임의로 해당 교수의 논문으로 추가하지 않는다** (원칙 2)

#### 교수–논문 저자 검증 절차 (v6.5 확정)

위 원칙을 **데이터 수집 단계에서 실제로 어떻게 보장하는지**를 확정한다. 아래는 기존 귀속 원칙을 구체화한 것이며, 공저 논문 귀속 정책을 바꾸지 않는다.

**A. 기준점 — `data/input/professor_paper_lists.json`의 인용문**

- 교수의 논문 귀속 여부는 **`data/input/professor_paper_lists.json`의 인용문을 신원 보증의 기준점으로 삼아** 판단한다
- **인용문에 있는 논문만 검증 대상**이다
- **인용문에 없는 논문은 저자명과 소속이 일치하더라도 자동으로 추가하지 않는다**
- 목적은 **동명이인 오귀속 위험을 방지**하는 것이다

**B. PubMed 검증 절차**

1. `data/input/professor_paper_lists.json`의 인용문에서 **논문 제목을 파싱**한다
2. 파싱한 제목으로 **PubMed 후보를 검색**한다
3. 후보 논문의 제목을 **`titles_match` 규칙으로 대조**한다
4. **`titles_match`를 통과한 후보만 채택 대상**으로 본다
5. **통과 후보가 2개 이상이면 자동 채택하지 않는다**
6. 후보가 2개 이상인 경우 사람이 확인하도록 **`review`에 남긴다**

> `titles_match`의 구체적인 알고리즘은 **이 계약에서 새로 정의하지 않는다.** 여기서 정하는 것은 **검증 단계에서 `titles_match`를 사용한다**는 계약까지이며, 판정 방식은 구현·기존 문서의 정의를 따른다.

**C. KCI 검증 조건**

- KCI 후보는 위 **A의 기준점과 검증 흐름 안에서** 다루며, 채택 시 **저자 소속에 전북대가 포함되는지를 추가로 확인**한다
- 저자 소속에 전북대가 **포함되지 않으면 채택하지 않는다**
- 이 조건은 **추가 확인 항목이지 독립적인 자동 귀속 경로가 아니다.** 이 조건만 만족한다고 해서 인용문 기준점을 건너뛰고 귀속하지 않는다

**D. 수동 제외 — `data/input/manual_exclusions.json`**

- 전건 대조 또는 수동 검수 과정에서 **오귀속으로 확인된 논문**은 `data/input/manual_exclusions.json`에 **근거와 함께 기록**한다
- **논문 채택 단계에서 `manual_exclusions.json`에 등록된 항목은 제외한다**

```text
오귀속 확인 → manual_exclusions.json에 근거 기록 → 채택 단계에서 제외
```

**E. 금지 — 인용문 밖 논문의 자동 귀속**

- 어떤 논문이 해당 교수의 논문처럼 보이거나 **저자명과 소속이 일치하더라도**, 기준 인용문에 없다면 **자동 수집·채택 범위에 새로 넣지 않는다**
- **"저자명 + 전북대 소속이 일치하니 이 교수 논문일 것이다"** 라는 추론만으로 자동 귀속하지 않는다
- 이는 위 **"동일 식별자 또는 저자명·소속 정보만으로 교수 귀속을 자동 판단하지 않는다"** 는 원칙과 같은 취지다

## 2. API 엔드포인트

프론트의 `api/professorApi.js` 함수와 1:1로 대응합니다.

**v6.5에서 바뀐 것과 바뀌지 않은 것**

- **엔드포인트 변경 없음** — 경로·메서드 그대로
- **요청 구조 변경 없음** — `query` · `filters` · `sort` · `minScore` · `page` · `pageSize` 그대로
- **응답 필드 구조 변경 없음** — 교수 상세(API ②)의 `papers` 식별자도 **v6.4와 같은 `pmid` / `kciId` 두 필드를 유지한다** (원칙 1 · 1-2)
- `keywords`는 **필드 이름·타입 모두 그대로**다. 배열을 채우는 규칙(MeSH 우선 → KCI fallback → `[]`)만 v6.5에서 확정되었다 (1-1)
- `latestPaper`·`keywordsKo`·`meshTerms`·`kciKeywords`는 **내부 필드이므로 어떤 응답에도 포함되지 않는다** (keyword 계열은 검색에는 사용된다 · 1-1)
- 즉 **v6.5에서 바뀐 것은 응답의 모양이 아니라, 응답 값을 만드는 정책과 프론트의 표시·링크 규칙이다**

| 계약 | 경로 | 프론트 함수 |
| --- | --- | --- |
| API ① 교수 검색·목록 조회 | `POST /api/professors/search` | `getProfessors(query, filters)` |
| API ② 교수 상세 조회 | `GET /api/professors/{id}` | `getProfessorById(id)` |
| API ③ 최근 연구 활동 교수 조회 | `GET /api/professors/featured` | `getFeaturedProfessors()` |

### API ① 교수 검색·목록 조회

- 트리거: 검색 버튼 / Enter, 필터 선택 시 즉시 재조회, 페이지 번호 클릭

요청:

```json
{
  "query": "심장",
  "filters": {
    "professorType": ["임상의학", "기초의학"],
    "favoriteIds": ["P-001", "P-008", "P-013"]
  },
  "sort": "relevance",
  "minScore": 0.3,
  "page": 1,
  "pageSize": 5
}
```

#### 요청 필드 기본값·제약

| 필드 | 타입 | 기본값 | 비고 |
| --- | --- | --- | --- |
| `query` | string | `""` | 빈 문자열이면 전체 목록 조회(browse) |
| `filters.professorType` | string[] | `[]` | 빈 배열이면 전체. 허용값: `기초의학` / `임상의학` / `의학교육학` / `인문사회의학` |
| `filters.favoriteIds` | string[] \| null | `null` | `null`·없음 = 찜 필터 OFF, `[]` = 찜 필터 ON + 찜 0명 → 결과 0 |
| `sort` | string | `"relevance"` | MVP는 `relevance`만 지원 |
| `minScore` | number | `0.3` (**개발용 임시값**) | 0 ~ 1 |
| `page` | number | `1` | 1 이상 |
| `pageSize` | number | `5` | 한 페이지에 보여줄 교수 수 |

응답:

```json
{
  "results": [],
  "total": 12,
  "page": 1,
  "pageSize": 5,
  "collectedAt": "2026-08-16"
}
```

- `results` — 교수 카드(1-1) 배열
- `total` — 모든 필터를 적용한 뒤의 최종 개수(페이지를 자르기 전 값). 프론트가 이 값으로 페이지 수 계산
- `page` · `pageSize` — 요청 값을 그대로 반환
- `collectedAt` — 데이터 수집 기준일 (`"YYYY-MM-DD"`). 요청마다 바뀌는 값이 아니다 (원칙 4)

#### 검색 대상 필드

`query`는 아래 필드에서 **부분일치(대소문자 무시)** 로 검색한다.

- 교수명 (`name`) · **keyword 계열** · `specialties` · 논문 제목 · **논문 초록** · 소속 (`department`)

**keyword 계열 — keyword 계열 전체의 합집합을 검색한다 (v6.5 확정)**

```text
검색 대상 keyword 계열
  = keywords ∪ keywordsKo ∪ meshTerms ∪ kciKeywords.ko ∪ kciKeywords.en
    (합친 뒤 중복 제거)
```

| 필드 | 검색에서의 역할 | API 응답 |
| --- | --- | --- |
| `keywords` | 화면·API용 **대표 영문** keyword 매칭 | **포함** |
| `keywordsKo` | 최종 `keywords`의 **한글 검색 대응값** | 미포함 (내부) |
| `meshTerms` | PubMed/MeSH **원본 영문** terms 매칭 | 미포함 (내부) |
| `kciKeywords.ko` | KCI가 제공한 **원본 한글** keyword 검색 지원 | 미포함 (내부) |
| `kciKeywords.en` | KCI가 제공한 **원본 영문** keyword 검색 지원 | 미포함 (내부) |

- 다섯 필드 모두 `professors.json` 내부에 있으며, 백엔드가 이 파일을 읽어 검색한다 (1-1 · 7장)
- **표시용 `keywords` 선택 규칙과 검색 범위는 분리되어 있다** — 표시용은 `meshTerms`/`kciKeywords.en` 중 하나를 고르지만, 검색은 **다섯 필드를 모두 합쳐** 쓴다 (1-1)
- **프론트는 이 내부 검색 구조를 알 필요가 없다.** 응답으로 받는 keyword 필드는 `keywords` 하나뿐이고, **API 응답에 `keywordsKo`·`meshTerms`·`kciKeywords`를 추가하지 않는다**

> ⚠️ 논문 초록 검색은 v6.2에서 계약으로 확정한 사항이며, 백엔드 검색 로직 반영이 필요하다.
> ⚠️ 논문 제목·초록은 대체로 **영문**인데 검색어는 한글인 경우가 많다. `keywords`도 **최종 영문 배열**이다 (1-1). keyword 쪽 간극은 위 내부 한글 필드(`keywordsKo` · `kciKeywords.ko`)가 메우고, 제목·초록 쪽 간극은 5장의 **검색어 별칭 규칙**으로 해결한다.
> ⚠️ 검색 매칭에는 **전체 `keywords`**를 쓴다. 카드에 4개만 보인다고 해서 매칭 대상이 줄어드는 것이 아니다 (v6.5 · 1-1).

#### 정렬 규칙

```text
query가 있는 경우: matchScore 내림차순 → 동점이면 이름 오름차순
query가 없는 경우: 이름 오름차순
```

- 동점 시 이름 오름차순을 쓰는 이유 — 순서가 흔들리면 페이지를 넘길 때 결과가 중복되거나 누락된다

#### 빈 검색어(`query: ""`) — 전체 목록 조회(browse)

`query: ""`는 검색 실패가 아니라 **전체 교수 목록 조회**로 간주한다.

| 항목 | 동작 |
| --- | --- |
| `filters.professorType` · `filters.favoriteIds` | 그대로 적용 |
| `matchScore` | `null` — 근거가 없으므로 지어내지 않는다 (원칙 2) |
| `minScore` | **적용하지 않는다** |
| 정렬 | **이름 오름차순** |
| 페이지네이션 | 필터·정렬을 마친 뒤 `page` / `pageSize` 기준으로 자른다 |
| `total` | 필터 적용 후 전체 결과 수 |

#### `minScore`

- 이 값 미만의 `matchScore`를 가진 교수는 백엔드가 결과에서 제외한다 (원칙 3)
- **현재 개발용 임시 기본값 `0.3`** — 최종 threshold는 5장 참고
- 빈 `query`에서는 적용하지 않는다

#### "찜한 교수만 보기" 필터 (`filters.favoriteIds`)

프론트가 localStorage의 찜 id 목록을 실어 보내면, 백엔드가 교집합(AND)을 걸어 최종 결과를 만든 뒤 페이지네이션한다.

```
① localStorage에서 찜 id 읽기   → ["P-001", "P-008", "P-013"]
② 검색 조건과 함께 백엔드 전달   → query + filters(favoriteIds 포함)
③ 백엔드가 교집합 계산          → query ∩ professorType ∩ 찜 id
④ 5명씩 페이지네이션            → page / pageSize
⑤ results + total 반환          → 찜 필터까지 반영된 최종 수
```

- **왜 프론트에서 거르지 않는가** — 백엔드가 먼저 자른 페이지를 프론트가 다시 거르면 `total`과 어긋나 페이지 계산이 깨진다
- 세 가지 상태: `null`(필터 꺼짐) / `[]`(필터 켜짐·찜 0명 → 결과 0) / `[id...]`(교집합)

**존재하지 않는 교수 id가 섞인 경우**

- 없는 id는 교집합에서 **제외**된다. 백엔드는 없는 교수를 만들어 채우지 않는다 (원칙 2)
- `total`은 실제로 존재하는 교수 수를 반환한다. 화면 표시 수는 언제나 응답의 `total`을 따른다

> ⚠️ v6.4에서 교수 DB 대상 범위가 좁아졌으므로(0-2장), 기존 localStorage에 범위 밖 교수 id가 남아 있을 수 있다. 위 규칙에 따라 자동으로 제외되며 별도 처리는 필요 없다.

**찜 목록 화면(FavoritesPage)**은 별도 API 없이 API ①을 재사용한다 — `query: ""` + `filters.favoriteIds`(항상 배열). browse 정책이 그대로 적용된다.

### API ② 교수 상세 조회

- 트리거: 카드의 [자세히 보기] 클릭
- 요청: `GET /api/professors/{id}` (예: `/api/professors/P-012`)
- 응답: 교수 상세 객체(1-2)
- 없는 id: HTTP 404 + `{ "error": "not_found" }`

### API ③ 최근 연구 활동 교수 조회

- 트리거: 메인 페이지 진입
- 요청: `GET /api/professors/featured`
- 응답: `{ "results": [ 교수 카드 배열 ], "collectedAt": "..." }`

#### 선정 기준

- 교수별 **가장 최근 PubMed 논문의 발행일** 최신순 상위 **3명** *(v6.5 — 산정 범위를 PubMed 논문으로 확정)*
- 후보가 되려면 그 논문에 **`pmid`와 `publishedAt`이 모두 확보되어 있어야 한다.** 둘 중 하나라도 없으면 그 논문은 후보가 아니고, 그런 논문이 하나도 없는 교수는 featured 후보에서 제외된다 (원칙 2 · 아래 산정 범위)
- 선정은 백엔드가 수행한다. 프론트는 받은 결과를 그대로 표시한다 (`slice` 금지)
- 선정용 내부 필드(`latestPaper`)는 **응답에 포함되지 않는다** (스키마는 아래 참고)
- 유효 후보가 3명 미만이면 **있는 만큼만** 반환한다 (가짜로 채우지 않는다)

##### `latestPaper` 산정 범위 (v6.5 확정)

`latestPaper`는 **API 응답 필드가 아니라 백엔드·데이터 파이프라인 내부의 featured 선정용 필드**다 (종전과 동일). 이 필드를 무엇으로 산정하는지를 v6.5에서 다음과 같이 확정한다.

**후보 조건 — `pmid`와 `publishedAt`을 모두 확보한 논문 (v6.5 확정)**

어떤 논문이 `latestPaper` 후보가 되려면 아래 **두 조건을 모두** 만족해야 한다.

1. **유효한 `pmid`가 있다** (PubMed 논문이다)
2. **완전한 `YYYY-MM-DD` 형식의 `publishedAt`을 확보했다** (featured 정렬 기준값 · 아래 부분 날짜 규칙)

| 논문 | `latestPaper` 후보 |
| --- | --- |
| `pmid` 있음 + `publishedAt` 있음 | **포함** |
| `pmid`와 `kciId`가 **모두** 있음 + `publishedAt` 있음 | **포함** — `pmid`가 있으므로 PubMed 논문이기도 하다 |
| `pmid` 있음 + **완전한 `publishedAt`을 확보하지 못함** (값 자체가 없거나, 연도-only·연월-only) | **제외** — 정렬 기준값이 없어 featured 순서를 정할 수 없다 (없는 값을 만들어 넣지 않는다) |
| `pmid`가 `null`이고 `kciId`만 있음 (KCI-only) | **제외** — `publishedAt`이 있어도 후보가 아니다 |

- 판별 기준은 **`pmid`의 존재 여부**와 **완전한 `YYYY-MM-DD` `publishedAt`의 확보 여부** 두 가지다. 어느 하나라도 없으면 후보가 아니다
- 교수별로 **위 두 조건을 모두 만족하는 PubMed 논문 중 가장 최근 논문**을 그 교수의 `latestPaper`로 사용한다
- 값이 없는 `publishedAt`을 추정해 채우거나 다른 값으로 대체하지 않는다 (원칙 2). 확보하지 못했으면 그 논문은 그냥 후보에서 빠진다

**부분 날짜(연도-only · 연월-only) 처리 (v6.5 확정)**

PubMed 원본의 발행일 정보는 **연도까지만**, 또는 **연·월까지만** 확보되는 경우가 있다. 이런 값은 **완전한 `publishedAt`으로 보지 않는다.**

| 조립 단계에서 확보한 날짜 | 날짜 조건 |
| --- | --- |
| `2019` (연도만) | **충족하지 않음 → `latestPaper` 후보 제외** |
| `2019-05` (연·월까지만) | **충족하지 않음 → `latestPaper` 후보 제외** |
| `2019-05-17` (완전한 `YYYY-MM-DD`) | **충족** |

- **존재하지 않는 월·일을 임의로 채워 `YYYY-MM-DD`를 만들지 않는다.** `2019` → `2019-01-01`, `2019-05` → `2019-05-01` 같은 보정은 **금지한다**
- 이유: 실제 발행일과 다른 날짜가 만들어져 **featured 최신순 정렬 결과가 왜곡될 수 있고**, "없는 값을 만들어 넣지 않는다"는 기존 정책(원칙 2)과도 충돌한다
- 따라서 **완전한 날짜를 확보할 수 없는 PubMed 논문은 `latestPaper` 후보에서 제외한다.** 그 논문이 `papers`에서 빠진다는 뜻은 아니다 (아래 `papers`의 범위 참고)
- 즉 **"`publishedAt`을 확보하지 못했다"** 에는 **① 값 자체가 없음 · ② 연도만 있음 · ③ 연-월까지만 있음** 이 모두 포함된다. **완전한 `YYYY-MM-DD`를 확보한 경우에만** 날짜 조건을 충족한다
- **교수에게 `pmid`와 `publishedAt`을 모두 확보한 후보 논문이 하나도 없으면 `latestPaper`를 산정할 수 없으므로 featured 후보에서 제외한다.** 여기에는 **PubMed 논문이 아예 없는 경우**(KCI-only 논문만 있는 교수 포함)뿐 아니라, **PubMed 논문은 있어도 그 논문들의 `publishedAt`을 하나도 확보하지 못한 경우**도 포함된다. 없는 값을 대체해 채우지 않는다 (원칙 2)
- **`pmid`의 존재 여부는 그 논문이 PubMed 논문인지를 판별하는 기준이다.** `pmid`가 있으면 PubMed 논문으로 분류되지만, **`latestPaper` 후보가 되려면 `publishedAt`도 함께 확보되어 있어야 한다.** `pmid`가 `null`이고 `kciId`만 있으면 KCI-only이므로 후보에서 제외한다 (1-2)
- **`pmid`와 `kciId`가 모두 있는 논문도 PubMed 논문이다.** 국내 학술지 논문이라도 PubMed에 등재되어 `pmid`를 가졌기 때문이며, `publishedAt`까지 확보되어 있으면 후보가 된다
- **KCI-only 논문을 후보에서 제외하므로, featured 선정에서 KCI 발행일과 PubMed 발행일을 서로 비교할 필요는 없다.** 또한 `latestPaper.publishedAt`은 **조립 단계에서 `YYYY-MM-DD` 형식으로 보장되므로**(아래 내부 스키마), featured 정렬에 들어가는 값들은 **모두 같은 날짜 정밀도**를 가진다 — 연도-only·연월-only 값을 섞어 비교하기 위한 별도 규칙이 필요하지 않다

##### `latestPaper` 내부 스키마 (v6.5 확정)

위 후보 조건을 만족하는 논문이 **있는** 경우 (교수 내부 레코드의 일부):

```json
{
  "latestPaper": {
    "pmid": "35123456",
    "publishedAt": "2025-03-14"
  }
}
```

후보 조건을 만족하는 논문이 **하나도 없는** 경우:

```json
{
  "latestPaper": null
}
```

| 필드 | 타입 | 의미 |
| --- | --- | --- |
| `latestPaper` | `object \| null` | featured 선정을 위한 **내부 필드**. **API 응답에는 포함하지 않는다** |
| `latestPaper.pmid` | `string` | 후보 조건을 만족하는 논문 중 **가장 최근 PubMed 논문의 PMID** |
| `latestPaper.publishedAt` | `string` (**`YYYY-MM-DD`**) | 해당 PubMed 논문의 **발행일**. featured 정렬 기준. **조립 단계에서 이 형식으로 보장한다** |

- **`pmid`와 완전한 `YYYY-MM-DD` `publishedAt`을 모두 확보한 PubMed 논문이 있을 때만 `latestPaper` object를 만든다**
- **KCI-only 논문은 `latestPaper`가 될 수 없다** (위 후보 조건)
- **`pmid`는 있지만 완전한 `publishedAt`을 확보하지 못한 논문도 `latestPaper`가 될 수 없다** — 값이 아예 없는 경우뿐 아니라 **연도-only·연월-only인 경우도 포함**한다 (위 부분 날짜 규칙)
- **후보 조건을 만족하는 논문이 하나도 없으면 `latestPaper = null`** 이고, 그 교수는 featured 후보에서 제외된다 (없는 값을 지어내지 않는다 · 원칙 2). PubMed 논문이 아예 없는 교수도 여기에 해당한다
- **featured 정렬은 `latestPaper.publishedAt` 기준**이다
- `latestPaper`는 내부 필드이므로 **API ③ 응답에 포함하지 않는다**

> **`latestPaper` 안에 `kciId`가 없는 이유** — 후보가 **PubMed 논문뿐이라 `pmid`가 반드시 존재**하기 때문이다. 후보 논문이 `kciId`를 함께 가지고 있더라도, featured 선정에 필요한 값은 `pmid`와 `publishedAt`뿐이므로 `latestPaper`에는 담지 않는다. 그 논문의 `kciId`는 `papers`(1-2)에 그대로 남아 있다.

> **`latestPaper.publishedAt`의 형식은 `YYYY-MM-DD`로 확정한다 (v6.5).** 위 `"2025-03-14"`는 이 계약 포맷과 일치하는 예시다.
>
> - **이는 "PubMed 원본 데이터가 항상 `YYYY-MM-DD`를 제공한다"는 일반적 사실 선언이 아니다.** 우리 **조립기가 `latestPaper` 내부 필드를 만들 때 보장하는 데이터 계약**이다
> - `latestPaper.publishedAt` 값들은 **모두 같은 날짜 정밀도**를 가지므로, featured 선정에서 **연도-only / 연월-only / 연월일 값을 서로 비교하기 위한 별도의 정밀도 비교 규칙은 필요하지 않다**
> - 이 보장은 **값이 존재할 때의 내부 형식**에 대한 것이다. **`publishedAt`을 확보하지 못한 논문에 값을 임의로 만들어 넣는다는 뜻이 아니며**, 그런 논문은 종전대로 후보에서 제외된다 (위 후보 조건 · 원칙 2)
> - **PubMed 원본이 부분 날짜(연도-only·연월-only)일 수 있다는 전제에서**, 조립기가 **완전한 `YYYY-MM-DD`를 확보한 경우에만** `latestPaper` 후보로 채택한다. 부족한 자리를 `01`로 채우지 않는다 (위 부분 날짜 규칙)

**`papers`의 범위와 혼동하지 않는다 — 두 범위는 서로 다르다**

| 구분 | 대상 범위 |
| --- | --- |
| 대표 논문 `papers` (1-2 · 응답 필드) | 기존 계약 그대로 — **PubMed 논문과 KCI-only 논문이 모두 포함될 수 있다** |
| featured 선정용 `latestPaper` (내부 필드) | **PubMed 논문만** |

- 즉 `latestPaper` 산정에서 KCI-only 논문을 제외한다는 것은 **featured 선정 기준에 한정된 규칙**이다. 교수 상세의 `papers`에서 KCI-only 논문을 빼라는 뜻이 **아니다** (3장 — `pmid`가 `null`이고 `kciId`만 있는 국내 논문도 목록에서 제거하지 않는다)

### 찜하기 · 찜 취소 · 찜 목록

- **찜 id의 저장·추가·삭제** — 백엔드 API 없음. localStorage (`getFavorites` / `addFavorite` / `removeFavorite`)
- **찜한 교수의 데이터 조회** — API ① (localStorage에는 id만 있으므로 표시할 데이터는 백엔드에서 받는다)
- `isFavorite` · `favoriteDate`는 mock 테스트용이며 계약 응답에 넣지 않는다

## 3. 프론트엔드 내부 처리 (백엔드 요청 불필요)

- 찜하기 / 찜 취소 / 찜 **id 목록 읽기** — localStorage
- 필터 초기화 — 검색어는 유지하고 교수 구분·찜 필터만 기본값으로. 페이지는 1로
- 페이지네이션 — 응답의 `total`로 페이지 계산, 페이지 클릭 시 `page`만 바꿔 API ① 재호출
- 찜 여부 표시 — `id`를 localStorage와 대조
- **`keywords` 표시 개수 제한** — 카드는 앞 4개 + `+N`, 상세는 전체 (1-1). 응답을 자르지 않고 표시 단계에서만 제한한다
- **논문 원문 링크 조립** — `pmid` / `kciId`로 주소를 만든다. 아래 참고

### 논문 원문 링크 (v6.5 확정)

**논문 URL 문자열은 데이터·API 응답에 저장하지 않는다.** 응답에는 식별자 `pmid` · `kciId`만 담고, 프론트가 아래 규칙으로 주소를 조립한다.

**링크 우선순위 — `pmid` 우선**

| 순위 | 조건 | 조립할 URL | 버튼 문구 |
| --- | --- | --- | --- |
| 1 | `pmid`가 있음 | `https://pubmed.ncbi.nlm.nih.gov/{pmid}/` | "PubMed 보기" |
| 2 | `pmid`가 `null`이고 `kciId`가 있음 | `https://www.kci.go.kr/kciportal/ci/sereArticleSearch/ciSereArtiView.kci?sereArticleSearchBean.artiId={kciId}` | "KCI 보기" |
| 3 | 둘 다 `null` | **계약상 응답에 존재하지 않는 논문** (원칙 1). 링크 버튼을 렌더링하지 않는다 | — |

- URL에 넣을 때는 **PubMed는 `encodeURIComponent(pmid)`, KCI는 `encodeURIComponent(kciId)`** 로 감싼다
- **두 식별자 모두 화면에 직접 표시하지 않는다.** 링크 생성에만 쓴다
- **계약상 `pmid`·`kciId`가 둘 다 없는 논문은 응답에 존재하지 않는다** (원칙 1). 그래도 프론트는 방어적으로 **둘 다 `null`이면 링크 버튼을 렌더링하지 않는다** — 주소를 지어내지 않기 위해서다 (원칙 2)
- **`kciId`만 있는 국내 논문도 목록에서 제거하지 않는다.** 식별자 종류로 논문을 거르면 국내 학술지 논문이 통째로 사라진다
- **둘 다 있는 논문은 `pmid`를 우선해 PubMed 링크를 만든다** (영문 초록·인용 정보가 함께 보이므로)

> **`pmid` 우선은 링크 버튼을 하나 고르는 규칙일 뿐이다.** API 응답에서 식별자를 하나만 남긴다는 뜻이 아니다 — `pmid`와 `kciId`는 둘 다 응답에 담긴다 (1-2).

## 4. 값 없음 처리 규칙 (원칙 2 · 빈칸 절대 금지)

**기본 원칙 — 타입에 따라 값의 부재를 다르게 표현한다 (v6.5 명시)**

| 필드 타입 | 값이 없을 때 |
| --- | --- |
| **값의 부재가 허용되는(nullable) 스칼라** — 아래 표에서 `null`로 표기된 필드 | **`null`** |
| **배열** (`string[]` 등) | **빈 배열 `[]`** |

- **모든 스칼라 필드가 `null`이 될 수 있다는 뜻이 아니다.** `id` · `name` 같은 **필수 스칼라 필드는 항상 값이 있어야 하며** `null`을 허용하지 않는다. 위 규칙은 **아래 표에 `null`로 명시된 nullable 필드**에 적용된다
- 배열 필드는 **값이 없어도 `null`로 보내지 않고, 필드를 생략하지도 않는다.** 항상 배열 타입을 유지한다
- 이는 일부 필드에만 적용되는 예외가 아니라 **이 계약에서 값의 부재를 표현하는 기본 원칙**이다. 내부 keyword 배열(`keywordsKo` · `meshTerms` · `kciKeywords.ko` · `kciKeywords.en`)에도 동일하게 적용된다 (1-1)

| 필드 | 값이 없을 때 | 화면 표시 |
| --- | --- | --- |
| `profileImageUrl` | `null` | 이니셜 아바타 |
| `email` | `null` | "정보 없음" |
| `homepageUrl` | `null` | 링크 숨김 |
| `papers` | `[]` | "등록된 대표 논문 없음" |
| `papers[].pmid` (`string \| null`) | `null` (PubMed에 없는 논문 — **KCI-only 논문에서는 정상 상태**) | 표시하지 않음 (원문 링크 생성에만 사용) |
| `papers[].kciId` (`string \| null`) | `null` (KCI에 없는 논문) | 표시하지 않음 (원문 링크 생성에만 사용) |
| `papers[].pmid` · `papers[].kciId` **동시** | **둘 다 `null`인 논문은 응답에 넣지 않는다** — 둘 중 최소 하나는 반드시 존재 (원칙 1) | 링크 버튼 미렌더링 (3장) |
| `specialties` | `[]` | 해당 영역 표시 생략 |
| `keywords` | `[]` — **`null`이나 필드 생략을 쓰지 않는다.** `meshTerms`와 `kciKeywords.en`이 **모두** 비었을 때 `[]`가 된다 (1-1) | **해당 키워드 영역 표시 생략 — 카드·상세 공통 (v6.5)** |
| `keywordsKo` · `meshTerms` · `kciKeywords.ko` · `kciKeywords.en` (**내부 필드**) | 각각 `[]` — **항상 필드가 존재하고 항상 배열이며, `null`·생략을 쓰지 않는다** (1-1) | 응답에 나가지 않으므로 화면 표시 없음 |
| `matchScore` | `null` (빈 검색어 · featured) | 점수 미표시 |
| 검색 결과 | `results: []`, `total: 0` | "검색 결과가 없습니다" |
| featured 결과 | 유효 후보가 3명 미만이면 있는 만큼만 | 받은 개수만큼 표시 |

> `labName` 행은 v6.4에서 삭제되었다 (필드 자체 제거).

**참고 — 데이터가 거의 비어 있는 교수**: 의대 명단에만 있는 교수(주로 기초의학)는 병원 프로필이 없어 `profileImageUrl`·`specialties`가 비어 있다. 논문은 KCI 등 후속 수집으로 보완될 수 있으며, `keywords`는 **`meshTerms` 우선 → 비어 있으면 `kciKeywords.en` → 둘 다 비어 있으면 `[]`** 규칙으로 채워진다 (v6.5 확정 · 1-1). 따라서 PubMed 논문이 없어 MeSH를 확보하지 못한 교수라도 KCI 영문 keyword가 있으면 `keywords`가 비지 않는다. **KCI keyword 수집은 완료되었으며, `kciKeywords.en`을 확보하지 못한 교수는 이 fallback에서도 `keywords`가 `[]`로 남는다** (1-1 참고). 카드에 이름·구분·소속만 표시되는 경우가 있으므로 프론트는 이 상태에서도 레이아웃이 깨지지 않아야 한다.

## 5. 아직 확정이 필요한 항목

1. **`matchScore` 최종 산식** — 계약상 `0~1` 실수(또는 `null`)로만 정의되며 계산 방법은 백엔드/검색엔진팀 소관. 현재 MVP 산식이 동작 중이나 팀 최종 확정은 아니다.
2. **`minScore` 최종 threshold** — 현재 `0.3`은 임시값. 산식이 확정되면 점수 분포에 맞춰 함께 정한다.
   - 실측 사례: `"통증"` 검색 시, 전문분야에 "통증"이 있는 교수가 소속명에 없다는 이유로 0.2점을 받아 임계값 0.3에서 제외됨. 가중치 또는 threshold 조정이 필요하다.
3. **검색어 별칭 규칙 (한↔영 · 학과/진료과)** — 2026-08-16 회의에서 도입은 결정, **구현은 마지막 단계**로 합의.
   - 목적 ①: 한글 검색어를 영문 데이터(논문 제목·초록, 그리고 MeSH를 쓰는 교수의 `keywords`)와 연결 (예: `심장` → `heart`, `cardiac`, `cardiovascular`)
   - 목적 ②: 같은 진료과의 표기 차이를 흡수 (예: `내과학교실(심장)` ↔ `심장내과`)
   - 방식: 별칭표를 미리 만들어 저장소에 두고 검색 시에는 조회만 한다. 표에 없는 검색어는 KMLE 1:1 번역 → AI 보완 순으로 처리한다
   - **이는 `검색어` 쪽에 별칭을 붙이는 규칙이며, `keywords` 값 자체를 번역·변환하는 것이 아니다.** `keywords`(특히 KCI keywords)에는 별도 번역 과정을 두지 않는다는 v6.5 확정 정책과 충돌하지 않는다 (1-1)
   - 미해결: 별칭표 파일 형식·관리 주체, 백엔드 검색 로직 반영 시점
4. **대표 논문 3편 선정 시 최신 논문과 인용수 상위 논문의 중복 처리 규칙** — 대표 논문은 "최신순 1편 + 인용수 상위 2편 = 3편"이고 인용수 기준은 확정되어 있으나(1-2 · OpenAlex 우선, 없으면 KCI 피인용수), **최신 1편이 동시에 인용수 상위 논문이기도 할 때** 3편을 어떻게 채울지는 정해져 있지 않다.
   - 미해결: 이미 선택된 논문을 제외하고 다음 순위를 채울지, 3편보다 적게 반환할지
   - **조립기 동작 확인 후 확정한다.** 그전까지 임의의 보충 규칙을 만들지 않는다 (원칙 2)
5. **featured 교수의 `latestPaper.publishedAt` 동점 정렬 규칙** — featured는 `publishedAt` 최신순 상위 3명이지만(2장 API ③), **두 명 이상의 `publishedAt`이 같을 때의 순서**는 정해져 있지 않다.
   - 참고: 2장 API ①의 "동점이면 이름 오름차순"은 **검색 결과(`matchScore`) 정렬 규칙**이며 featured에는 적용 범위가 다르다
   - 미해결: featured 동점 시 tie-break 기준
   - `publishedAt`이 `YYYY-MM-DD`로 통일되어(2장 API ③) **같은 날짜의 동점 자체는 여전히 발생할 수 있다.** 포맷 확정이 이 항목을 해결하지는 않는다
   - 페이지네이션이 없는 API ③에서는 영향이 제한적이지만, 상위 3명의 경계에서 결과가 흔들릴 수 있다
   - **조립기 동작 확인 후 확정한다**
6. **`keywords` 배열의 정렬 규칙 (백엔드/조립기)** — 백엔드·조립기가 최종 `keywords` 배열을 **어떤 순서로 생성해야 하는지**는 확정되지 않았다.
   - **왜 필요한가**: 교수 카드는 배열의 **앞 4개**를 표시하고 초과분을 `+N`으로 처리하므로(1-1), **배열 순서가 화면에 어떤 keyword가 노출되는지를 직접 결정한다**
   - **프론트는 받은 순서를 재정렬하지 않으므로**(1-1 · 확정), **백엔드/조립기가 안정적인 순서를 제공해야 한다.** 순서를 정할 책임은 프론트가 아니라 백엔드·데이터 조립 단계에 있다
   - **동일한 데이터로 다시 조립했을 때 순서가 임의로 바뀌지 않는, 재현 가능한 정렬 규칙이 필요하다.** 조립할 때마다 순서가 흔들리면 같은 교수의 카드에 보이는 keyword가 배포마다 달라진다
   - 미해결: 어떤 기준으로 정렬할지, 동률일 때의 tie-break
   - **현재 검토 중인 제안 (확정 아님 · 참고용 기록)**: "해당 교수의 논문 전체에서 keyword 등장 빈도가 높은 순 → 빈도가 같으면 알파벳순". 자주 등장하는 연구 주제를 카드 앞쪽에 배치하고 동률에서도 재현 가능한 결과를 얻으려는 의도다. **아직 채택된 규칙이 아니므로 이 방식을 전제로 구현하지 않는다**
   - **현재 조립기의 실제 동작을 확인한 뒤 최종 정렬 규칙을 확정할 예정이다** (위 4·5번과 함께 백엔드 담당자가 회신)

> **MeSH 미확보 교수의 `keywords` 보완 정책은 v6.5에서 확정되어 이 목록에서 내려왔습니다.** 아래 표의 `keywords` 데이터 선택 정책 행과 1-1을 따릅니다.
> **`latestPaper.publishedAt` 포맷·날짜 비교 규칙**과 **KCI keywords 한글/영문 선택 및 배열 구성 규칙**도 이 개정에서 확정되어 이 목록에서 내려왔습니다 — 아래 표의 해당 행과 1-1 · 2장 API ③을 따릅니다.
> **교수–논문 저자 검증의 구체적 절차**도 이 개정에서 현재 구현 기준으로 확정되어 이 목록에서 내려왔습니다 — 1-2의 `교수–논문 저자 검증 절차`를 따릅니다.
> **4·5·6번은 백엔드 담당자가 현재 조립기 동작을 확인한 뒤 함께 회신하기로 한 항목입니다.** 회신 전까지 이 세 항목에 대해 합리적으로 보이는 기본값을 임의로 확정하지 않습니다.

| 4. 찜 목록 | localStorage(`getFavorites`) + API ① `getProfessors("", { filters: { favoriteIds } })` |
| 5. 로그인 | MVP 미구현 |

`keywords` 표시 개수는 화면이 아니라 **컴포넌트 기준**이다 — 1·2·4번 화면은 같은 교수 카드 컴포넌트를 쓰므로 모두 앞 4개 + `+N`, 3번 상세만 전체 표시다 (1-1).

## 7. 데이터 갱신 · 배포 구성 (v6.4 신설 · 2026-08-16 회의 확정)

계약 데이터가 어떻게 만들어지고 서비스에 닿는지에 대한 합의 사항이다.

```
[데이터 수집 서버(고정 IP)]  주기 실행(cron) → 수집·조립 → professors.json
                              └ 백엔드(FastAPI)가 같은 서버에서 이 파일을 읽어 API 제공
                                        ↑ HTTPS
[Vercel]  프론트엔드 정적 배포 — 학생이 접속
```

- **서비스 런타임에는 외부 API를 호출하지 않는다.** 백엔드는 완성된 `professors.json`만 읽는다. PubMed·OpenAlex·KCI 장애가 검색 기능에 영향을 주지 않는다
- 수집은 별도 주기로 동작한다 (논문·인용수 주 1회 / 교수 명단 월 1회 예정)
- **KCI API 인증키는 IP에 묶여 있어** 수집은 고정 IP 서버에서만 가능하다. Vercel·GitHub Actions는 IP가 유동이라 KCI 호출에 사용할 수 없다
- `professors.json`에는 교수 이메일이 포함되므로 **공개 저장소에 커밋하지 않는다.** 파일은 담당자가 별도 채널로 전달하거나, 수집 서버에서 직접 생성해 사용한다
- `collectedAt`은 이 파일이 만들어진 날짜다 (원칙 4)
