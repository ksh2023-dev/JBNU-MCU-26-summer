## 0. 대전제

### 0-1. 할루시네이션 방지 4원칙

이 프로젝트는 없는 값을 지어내는 순간 서비스가 실패합니다. 아래 4원칙은 백엔드가 응답을 만들 때, 그리고 AI로 데이터를 수집·정리·생성할 때 반드시 지킵니다.

1. **모든 논문에는 `pmid` 또는 `kciId`가 필수.** 둘 다 없는 논문은 응답에 넣지 않는다. *(v6.4 개정 — 기존 "pmid 필수"에서 확장)*
2. 값이 없는 필드는 지어내지 말고 `null`로 보낸다. (화면 표시 문구 "정보 없음"은 프론트가 붙인다. 빈칸으로 두지 않는다)
3. **검색어가 있는 경우**, `matchScore`가 임계값(`minScore`) 미만인 교수는 결과에서 제외한다. 억지로 채우지 않는다.
   - 빈 검색어(`query: ""`) 전체 조회에서는 `matchScore`가 `null`이라 임계값 비교가 불가능하므로 `minScore`를 적용하지 않는다. (2장 API ① browse 정책)
4. 응답에 데이터 수집 기준일(`collectedAt`)을 담는다. 교수명·이메일·논문 값은 DB 원본 그대로, 재작성 금지.

AI로 데이터를 만들 때 프롬프트 맨 앞에 붙일 규칙 (그대로 복사):

```
너는 <교수_데이터> 안의 값만 사용한다.
- 데이터에 없는 교수·논문·연구실·이메일·ORCID를 절대 생성하지 마라.
- 값이 없으면 지어내지 말고 null로 두어라.
- 논문은 pmid 또는 kciId가 있는 것만 포함하라. 제목·학술지·연도는 원본 그대로 두어라.
- 근거가 부족하면 "제공된 데이터로는 확인할 수 없습니다"라고만 답하라.
```

### 0-2. 교수 DB 대상 범위 (v6.4 신설 · 2026-08-16 회의 확정)

**전북대학교 의과대학 공식 명단(교실/교수 페이지)에 게시된 교수를 대상으로 한다.**

| 구분 | 처리 | 사유 |
| --- | --- | --- |
| 의대 명단 게시 교수 | **포함** | 기준 명단 |
| 치과 계열 진료과 소속 | **제외** | 의과대학 소속이 아님 |
| 병원 명단에만 있고 의대 명단에 없는 교수 | **제외** | 의대 공식 명단 기준에 해당하지 않음 |

- 현재 수록 인원: **182명** (임상의학 145 · 기초의학 35 · 의학교육학 1 · 인문사회의학 1)
- 제외된 교수의 데이터는 삭제하지 않고 파이프라인 산출물에 보존한다. 범위가 변경되면 재조립으로 복구된다
- 범위 변경은 계약 개정 사항이다. 임의로 바꾸지 않는다

## 1. 공통 데이터 객체

### 1-1. 교수 카드 (검색 결과 · featured 1건)

```json
{
  "id": "P-012",
  "name": "김민수",
  "profileImageUrl": null,
  "professorType": "임상의학",
  "department": "순환기내과",
  "specialties": ["심장영상", "심부전"],
  "keywords": ["cardiac imaging", "heart failure", "biomarker"],
  "matchScore": 0.87
}
```

- 같은 모양을 교수 검색 결과와 featured(최근 연구 활동 교수)에서 공통으로 사용
- `id` — 내부 식별자, 화면에는 표시하지 않음. **한 번 부여되면 변경되지 않는다** (프론트 찜이 localStorage에 id로 저장되므로)
- `profileImageUrl` — 없으면 `null` (프론트가 이니셜 아바타로 대체)
- `professorType` — 교수 구분 필터값. 값 집합: `기초의학 | 임상의학 | 의학교육학 | 인문사회의학`
- `department` — 소속교실 또는 진료과. **분과·겸직이 병기될 수 있다** (예: `내과학교실(소화기)`, `예방의학교실 · 가정의학교실`)
- `specialties` — 전문 분야. 여러 개를 담는 배열(`[ ]`). 값이 하나여도 배열로 보냄. 없으면 빈 배열 `[]`
- `keywords` — **응답에는 전체 배열을 담고, 카드 화면에는 앞 4개까지 표시한다 (v6.5)**. 아래 참고
- `matchScore` — **`number | null`** (아래 참고)
- 찜 여부·이메일은 카드에 넣지 않음 — 찜 여부는 프론트가 `id`를 localStorage와 대조해 판단, 이메일은 상세에서만 표시

#### `keywords` — MeSH 기반 영문 키워드 + 화면 표시 정책 (v6.5 확정)

**데이터의 성격 — v6.4와 동일 (변경 없음)**

- **`keywords`는 논문 MeSH 용어 기반의 영문 키워드다** (예: `"cardiac imaging"`). v6.5에서 확정된 정책이며, 값의 언어·출처는 이대로 유지한다
- **백엔드는 전체 배열을 응답에 담는다.** 개수를 잘라서 보내지 않는다
- **검색 매칭에는 전체 `keywords`를 사용한다.** 화면에 몇 개를 보여주는지와 무관하다
- 한글 검색어와 영문 값 사이의 간극은 5장의 **검색어 별칭 규칙**으로 해결한다 — `keywords` 자체를 바꾸는 것이 아니라, 검색어 쪽에서 별칭을 붙여 매칭한다

**화면 표시 정책 — v6.5 신설 (v6.4의 "화면 미표시"를 대체)**

| 화면 | 표시 |
| --- | --- |
| 교수 카드 — HomePage · SearchResultPage · FavoritesPage | 응답 배열의 **순서를 유지한 채 앞 4개까지** |
| 교수 카드에서 4개를 초과할 때 | 나머지 개수를 **`+N`** 으로 표시 (예: 총 7개 → 앞 4개 + `+3`) |
| 교수 상세 — ProfessorDetailPage | **전체 표시** (자르지 않는다) |
| `keywords: []` | 카드·상세 **모두 해당 키워드 영역을 표시하지 않는다** |

- 위 세 화면은 같은 `ProfessorCard` 컴포넌트를 쓴다. **표시 개수 제한은 `ProfessorCard` 한 곳에서만 한다** — 페이지가 미리 잘라서 넘기면 같은 교수 데이터가 화면마다 다르게 보이고, `+N`도 이미 잘린 배열 길이로 계산되어 실제 개수와 어긋난다
- **`keywords` 배열의 순서는 백엔드가 응답으로 제공한 순서를 그대로 사용한다.** 프론트는 중요도·관련도를 재계산하거나 배열을 재정렬하지 않고, 그 순서 위에서 "표시 개수"만 앞에서 자른다
- 백엔드 내부의 `keywords` 정렬·우선순위 산정 방식은 **프론트 화면 표시 계약의 범위 밖**이다. 프론트 구현을 위해 그 결정을 기다릴 필요는 없다

> 카드 앞 4개 + `+N`, 상세 전체 표시라는 v6.5 `keywords` 화면 정책은 이 내용으로 완결된다.

#### `matchScore` — `number | null` (v6.2 확정, 변경 없음)

| 상황 | 값 |
| --- | --- |
| 검색어가 있는 검색 결과 (`query`에 값 있음) | `0 ~ 1` 사이 실수 (관련도 점수) |
| 빈 검색어 전체 조회 (`query: ""`) | `null` |
| featured 교수 카드 (API ③) | `null` |

- **`matchScore: null`은 오류가 아니라 정상 상태다.** 검색어가 없어 관련도를 계산하지 않았다는 뜻이다 (원칙 2·3)
- 프론트는 `matchScore`가 항상 숫자라고 가정하지 않는다. 현재 카드 UI는 점수를 표시하지 않는다

### 1-2. 교수 상세

```json
{
  "id": "P-012",
  "name": "김민수",
  "profileImageUrl": null,
  "professorType": "임상의학",
  "department": "순환기내과",
  "specialties": ["심장영상", "심부전"],
  "keywords": ["cardiac imaging", "heart failure", "biomarker"],
  "email": "kim@jbnu.ac.kr",
  "homepageUrl": null,
  "papers": [
    { "title": "Prognostic value of cardiac MRI ...", "journal": "JACC", "year": 2022,
      "pmid": "35123456", "kciId": null },
    { "title": "국내 심부전 환자의 예후 인자 분석", "journal": "대한내과학회지", "year": 2021,
      "pmid": null, "kciId": "ART002712345" }
  ]
}
```

- 위쪽 `id` ~ `keywords`는 카드(1-1)와 동일한 칸 이름을 사용
- `keywords` — 응답은 카드와 같은 **전체 배열**이고, 상세 화면에서는 **자르지 않고 전체를 표시한다 (v6.5)**. 빈 배열 `[]`이면 키워드 영역 자체를 표시하지 않는다
- **`labName` 필드는 v6.4에서 삭제되었다.** 수집 가능한 출처가 없어 전원 `null`이었고, 프론트 화면에서도 제거하기로 확정(2026-08-16 회의)
- `homepageUrl` · `email` — 데이터 없으면 `null`
- `homepageUrl` — 임상 교수는 병원 프로필, 기초 교수는 학교 홈페이지 URL
- `papers` — 최신순 1편 + 인용수 상위 2편 = 3편 (7/23 회의 결정). 논문이 없으면 빈 배열 `[]`

#### `papers`의 논문 식별자 (v6.4 개정 · v6.5 보완)

각 논문은 **`pmid` 또는 `kciId` 중 최소 하나를 반드시 가진다.** 둘 다 없는 논문은 응답에 넣지 않는다(원칙 1).

| 필드 | 의미 | 값이 없을 때 |
| --- | --- | --- |
| `pmid` | PubMed 논문 고유번호 | `null` |
| `kciId` | KCI(한국학술지인용색인) 논문 고유 ID (`ART...` 형식) | `null` |

- 국제 학술지 논문은 대개 `pmid`만, 국내 학술지 논문은 `kciId`만 가진다
- **국내 학술지 중 PubMed에도 등재된 논문은 둘 다 가진다** (아래 중복 처리 규칙)
- 두 값 모두 화면에 표시하지 않는다. **링크 생성에만 사용한다** (3장 참고)
- **논문 URL 문자열은 데이터·API 응답에 저장하지 않는다 (v6.5).** `papers`에는 식별자만 담고, 주소는 프론트가 조립한다 (3장)

#### PubMed · KCI 중복 논문 처리 (v6.4 신설)

일부 국내 학술지(J Korean Med Sci, Korean J Intern Med 등)는 PubMed에도 등재되어 있어 같은 논문이 양쪽에서 수집될 수 있다. 파이프라인은 아래 규칙으로 하나의 논문으로 합친다.

**동일 논문 판별 (우선순위 순)**

1. **DOI 일치** — 양쪽 모두 DOI를 제공하므로 최우선 기준
2. DOI가 없으면 **정규화한 제목 + 발행연도** 일치 (대소문자·공백·구두점 무시, 영문 제목 우선 비교)
3. 그래도 판별이 어려우면 **별개 논문으로 두고 검수 목록에 기록한다.** 임의로 합치지 않는다 (원칙 2)

**병합 정책**

- 중복 판정 시 레코드를 하나로 합치고 **`pmid`와 `kciId`를 모두 보존**한다
- 대표 논문 3편 선정의 인용수 기준: **국제 인용수(OpenAlex) 우선, 없으면 KCI 피인용수**
- 초록·키워드는 영문(PubMed·MeSH)과 한글(KCI)을 내부 데이터로 함께 보존한다 (검색 매칭에 활용)

## 2. API 엔드포인트

프론트의 `api/professorApi.js` 함수와 1:1로 대응합니다. **v6.5에서 엔드포인트·요청 필드·응답 필드 변경은 없습니다.**

| 계약 | 경로 | 프론트 함수 |
| --- | --- | --- |
| API ① 교수 검색·목록 조회 | `POST /api/professors/search` | `getProfessors(query, filters)` |
| API ② 교수 상세 조회 | `GET /api/professors/{id}` | `getProfessorById(id)` |
| API ③ 최근 연구 활동 교수 조회 | `GET /api/professors/featured` | `getFeaturedProfessors()` |

### API ① 교수 검색·목록 조회

- 트리거: 검색 버튼 / Enter, 필터 선택 시 즉시 재조회, 페이지 번호 클릭

요청:

```json
{
  "query": "심장",
  "filters": {
    "professorType": ["임상의학", "기초의학"],
    "favoriteIds": ["P-001", "P-008", "P-013"]
  },
  "sort": "relevance",
  "minScore": 0.3,
  "page": 1,
  "pageSize": 5
}
```

#### 요청 필드 기본값·제약

| 필드 | 타입 | 기본값 | 비고 |
| --- | --- | --- | --- |
| `query` | string | `""` | 빈 문자열이면 전체 목록 조회(browse) |
| `filters.professorType` | string[] | `[]` | 빈 배열이면 전체. 허용값: `기초의학` / `임상의학` / `의학교육학` / `인문사회의학` |
| `filters.favoriteIds` | string[] \| null | `null` | `null`·없음 = 찜 필터 OFF, `[]` = 찜 필터 ON + 찜 0명 → 결과 0 |
| `sort` | string | `"relevance"` | MVP는 `relevance`만 지원 |
| `minScore` | number | `0.3` (**개발용 임시값**) | 0 ~ 1 |
| `page` | number | `1` | 1 이상 |
| `pageSize` | number | `5` | 한 페이지에 보여줄 교수 수 |

응답:

```json
{
  "results": [],
  "total": 12,
  "page": 1,
  "pageSize": 5,
  "collectedAt": "2026-08-16"
}
```

- `results` — 교수 카드(1-1) 배열
- `total` — 모든 필터를 적용한 뒤의 최종 개수(페이지를 자르기 전 값). 프론트가 이 값으로 페이지 수 계산
- `page` · `pageSize` — 요청 값을 그대로 반환
- `collectedAt` — 데이터 수집 기준일 (`"YYYY-MM-DD"`). 요청마다 바뀌는 값이 아니다 (원칙 4)

#### 검색 대상 필드

`query`는 아래 필드에서 **부분일치(대소문자 무시)** 로 검색한다.

- 교수명 (`name`) · `keywords` · `specialties` · 논문 제목 · **논문 초록** · 소속 (`department`)

> ⚠️ 논문 초록 검색은 v6.2에서 계약으로 확정한 사항이며, 백엔드 검색 로직 반영이 필요하다.
> ⚠️ `keywords`·논문 제목·초록은 **영문**이고 검색어는 한글인 경우가 많다. 이 간극은 5장의 **검색어 별칭 규칙**으로 해결한다.
> ⚠️ 검색 매칭에는 **전체 `keywords`**를 쓴다. 카드에 4개만 보인다고 해서 매칭 대상이 줄어드는 것이 아니다 (v6.5 · 1-1).

#### 정렬 규칙

```text
query가 있는 경우: matchScore 내림차순 → 동점이면 이름 오름차순
query가 없는 경우: 이름 오름차순
```

- 동점 시 이름 오름차순을 쓰는 이유 — 순서가 흔들리면 페이지를 넘길 때 결과가 중복되거나 누락된다

#### 빈 검색어(`query: ""`) — 전체 목록 조회(browse)

`query: ""`는 검색 실패가 아니라 **전체 교수 목록 조회**로 간주한다.

| 항목 | 동작 |
| --- | --- |
| `filters.professorType` · `filters.favoriteIds` | 그대로 적용 |
| `matchScore` | `null` — 근거가 없으므로 지어내지 않는다 (원칙 2) |
| `minScore` | **적용하지 않는다** |
| 정렬 | **이름 오름차순** |
| 페이지네이션 | 필터·정렬을 마친 뒤 `page` / `pageSize` 기준으로 자른다 |
| `total` | 필터 적용 후 전체 결과 수 |

#### `minScore`

- 이 값 미만의 `matchScore`를 가진 교수는 백엔드가 결과에서 제외한다 (원칙 3)
- **현재 개발용 임시 기본값 `0.3`** — 최종 threshold는 5장 참고
- 빈 `query`에서는 적용하지 않는다

#### "찜한 교수만 보기" 필터 (`filters.favoriteIds`)

프론트가 localStorage의 찜 id 목록을 실어 보내면, 백엔드가 교집합(AND)을 걸어 최종 결과를 만든 뒤 페이지네이션한다.

```
① localStorage에서 찜 id 읽기   → ["P-001", "P-008", "P-013"]
② 검색 조건과 함께 백엔드 전달   → query + filters(favoriteIds 포함)
③ 백엔드가 교집합 계산          → query ∩ professorType ∩ 찜 id
④ 5명씩 페이지네이션            → page / pageSize
⑤ results + total 반환          → 찜 필터까지 반영된 최종 수
```

- **왜 프론트에서 거르지 않는가** — 백엔드가 먼저 자른 페이지를 프론트가 다시 거르면 `total`과 어긋나 페이지 계산이 깨진다
- 세 가지 상태: `null`(필터 꺼짐) / `[]`(필터 켜짐·찜 0명 → 결과 0) / `[id...]`(교집합)

**존재하지 않는 교수 id가 섞인 경우**

- 없는 id는 교집합에서 **제외**된다. 백엔드는 없는 교수를 만들어 채우지 않는다 (원칙 2)
- `total`은 실제로 존재하는 교수 수를 반환한다. 화면 표시 수는 언제나 응답의 `total`을 따른다

> ⚠️ v6.4에서 교수 DB 대상 범위가 좁아졌으므로(0-2장), 기존 localStorage에 범위 밖 교수 id가 남아 있을 수 있다. 위 규칙에 따라 자동으로 제외되며 별도 처리는 필요 없다.

**찜 목록 화면(FavoritesPage)**은 별도 API 없이 API ①을 재사용한다 — `query: ""` + `filters.favoriteIds`(항상 배열). browse 정책이 그대로 적용된다.

### API ② 교수 상세 조회

- 트리거: 카드의 [자세히 보기] 클릭
- 요청: `GET /api/professors/{id}` (예: `/api/professors/P-012`)
- 응답: 교수 상세 객체(1-2)
- 없는 id: HTTP 404 + `{ "error": "not_found" }`

### API ③ 최근 연구 활동 교수 조회

- 트리거: 메인 페이지 진입
- 요청: `GET /api/professors/featured`
- 응답: `{ "results": [ 교수 카드 배열 ], "collectedAt": "..." }`

#### 선정 기준

- 교수별 **가장 최근 논문의 발행일** 최신순 상위 **3명**
- 발행일 정보가 없는 교수는 후보에서 제외한다 (원칙 2)
- 선정은 백엔드가 수행한다. 프론트는 받은 결과를 그대로 표시한다 (`slice` 금지)
- 선정용 내부 필드(`latestPaper`)는 **응답에 포함되지 않는다**
- 유효 후보가 3명 미만이면 **있는 만큼만** 반환한다 (가짜로 채우지 않는다)

### 찜하기 · 찜 취소 · 찜 목록

- **찜 id의 저장·추가·삭제** — 백엔드 API 없음. localStorage (`getFavorites` / `addFavorite` / `removeFavorite`)
- **찜한 교수의 데이터 조회** — API ① (localStorage에는 id만 있으므로 표시할 데이터는 백엔드에서 받는다)
- `isFavorite` · `favoriteDate`는 mock 테스트용이며 계약 응답에 넣지 않는다

## 3. 프론트엔드 내부 처리 (백엔드 요청 불필요)

- 찜하기 / 찜 취소 / 찜 **id 목록 읽기** — localStorage
- 필터 초기화 — 검색어는 유지하고 교수 구분·찜 필터만 기본값으로. 페이지는 1로
- 페이지네이션 — 응답의 `total`로 페이지 계산, 페이지 클릭 시 `page`만 바꿔 API ① 재호출
- 찜 여부 표시 — `id`를 localStorage와 대조
- **`keywords` 표시 개수 제한** — 카드는 앞 4개 + `+N`, 상세는 전체 (1-1). 응답을 자르지 않고 표시 단계에서만 제한한다
- **논문 원문 링크 조립** — 아래 참고

### 논문 원문 링크 (v6.5 확정)

**논문 URL 문자열은 데이터·API 응답에 저장하지 않는다.** 응답에는 식별자(`pmid` / `kciId`)만 담고, 프론트가 아래 규칙으로 주소를 조립한다.

| 조건 | 조립할 URL | 버튼 문구 |
| --- | --- | --- |
| `pmid`가 있음 | `https://pubmed.ncbi.nlm.nih.gov/{pmid}/` | "PubMed 보기" |
| `pmid`가 `null`이고 `kciId`가 있음 | `https://www.kci.go.kr/kciportal/ci/sereArticleSearch/ciSereArtiView.kci?sereArticleSearchBean.artiId={kciId}` | "KCI 보기" |
| 둘 다 `null` | 없음 | **링크 버튼을 그리지 않는다** |

- 둘 다 있는 논문은 **PubMed를 우선**한다 (영문 초록·인용 정보가 함께 보이므로)
- 둘 다 `null`인 논문은 계약상 응답에 존재하지 않는다 (원칙 1). 그래도 프론트는 방어적으로 링크 버튼을 그리지 않는다 — 주소를 지어내지 않기 위해서다 (원칙 2)
- **`pmid`·`kciId` 식별자 자체는 화면에 표시하지 않는다.** 링크 생성에만 쓴다
- 식별자를 URL에 넣을 때는 `encodeURIComponent`로 감싼다
- **`kciId`만 있는 국내 논문도 목록에서 제거하지 않는다.** `pmid` 유무로 논문을 거르면 국내 학술지 논문이 통째로 사라진다

## 5. 아직 확정이 필요한 항목

1. **`matchScore` 최종 산식** — 계약상 `0~1` 실수(또는 `null`)로만 정의되며 계산 방법은 백엔드/검색엔진팀 소관. 현재 MVP 산식이 동작 중이나 팀 최종 확정은 아니다.
2. **`minScore` 최종 threshold** — 현재 `0.3`은 임시값. 산식이 확정되면 점수 분포에 맞춰 함께 정한다.
   - 실측 사례: `"통증"` 검색 시, 전문분야에 "통증"이 있는 교수가 소속명에 없다는 이유로 0.2점을 받아 임계값 0.3에서 제외됨. 가중치 또는 threshold 조정이 필요하다.
3. **검색어 별칭 규칙 (한↔영 · 학과/진료과)** — 2026-08-16 회의에서 도입은 결정, **구현은 마지막 단계**로 합의.
   - 목적 ①: 한글 검색어를 영문 데이터(`keywords`·논문 제목·초록)와 연결 (예: `심장` → `heart`, `cardiac`, `cardiovascular`)
   - 목적 ②: 같은 진료과의 표기 차이를 흡수 (예: `내과학교실(심장)` ↔ `심장내과`)
   - 방식: 별칭표를 미리 만들어 저장소에 두고 검색 시에는 조회만 한다. 표에 없는 검색어는 KMLE 1:1 번역 → AI 보완 순으로 처리한다
   - 미해결: 별칭표 파일 형식·관리 주체, 백엔드 검색 로직 반영 시점
4. **MeSH 미확보 교수의 `keywords` 보완 정책** — PubMed 논문이 없어 MeSH를 확보할 수 없는 교수는 현재 `keywords: []`가 될 수 있다. KCI-only 교수의 연구 키워드를 어떻게 보완할지는 아직 확정되지 않았다.
   - 후보 방식 ①: MeSH가 없으면 `keywords: []`를 그대로 유지한다
   - 후보 방식 ②: KCI에서 제공하는 키워드를 활용한다
   - 후보 방식 ③: KCI 키워드를 영문으로 정규화·변환해 활용한다
   - 후보 방식 ④: 검색용 `keywords`와 화면 표시용 키워드를 필드로 분리한다
   - 이 결정은 데이터/백엔드팀과 추가 논의 후 확정한다
   - **확정 전까지 프론트는 받은 `keywords` 배열만 표시하며, 없는 값을 임의로 생성하지 않는다** (원칙 2). `keywords: []`이면 해당 영역을 숨긴다 (1-1)
   - 이 항목은 **보완 방식**에 대한 논의이며, 1-1의 v6.5 확정 정책(MeSH 기반 영문 키워드 · 전체 배열 응답 · 카드 앞 4개 + `+N` · 상세 전체 표시)은 그대로 유지된다

### 이미 결정되어 이 목록에서 내려온 항목

| 항목 | 결정 |
| --- | --- |
| `keywords` 데이터 성격 | **확정 (v6.5)** — MeSH 기반 **영문 키워드**. 백엔드는 **전체 배열**을 응답에 담고, 검색 매칭에도 전체를 사용 (1-1) |

## 6. 화면 ↔ API 매핑

| 화면 | 사용하는 것 |
| --- | --- |
| 1. 메인(교수 검색) | `getProfessors`(검색), `getFeaturedProfessors` |
| 2. 검색 결과 | `getProfessors` → 교수 카드(1-1) |
| 3. 교수 상세 | `getProfessorById` |
| 4. 찜 목록 | localStorage(`getFavorites`) + API ① `getProfessors("", { filters: { favoriteIds } })` |
| 5. 로그인 | MVP 미구현 |

`keywords` 표시 개수는 화면이 아니라 **컴포넌트 기준**이다 — 1·2·4번 화면은 같은 교수 카드 컴포넌트를 쓰므로 모두 앞 4개 + `+N`, 3번 상세만 전체 표시다 (1-1).

## 7. 데이터 갱신 · 배포 구성 (v6.4 신설 · 2026-08-16 회의 확정)

계약 데이터가 어떻게 만들어지고 서비스에 닿는지에 대한 합의 사항이다.

```
[데이터 수집 서버(고정 IP)]  주기 실행(cron) → 수집·조립 → professors.json
                              └ 백엔드(FastAPI)가 같은 서버에서 이 파일을 읽어 API 제공
                                        ↑ HTTPS
[Vercel]  프론트엔드 정적 배포 — 학생이 접속
```

- **서비스 런타임에는 외부 API를 호출하지 않는다.** 백엔드는 완성된 `professors.json`만 읽는다. PubMed·OpenAlex·KCI 장애가 검색 기능에 영향을 주지 않는다
- 수집은 별도 주기로 동작한다 (논문·인용수 주 1회 / 교수 명단 월 1회 예정)
- **KCI API 인증키는 IP에 묶여 있어** 수집은 고정 IP 서버에서만 가능하다. Vercel·GitHub Actions는 IP가 유동이라 KCI 호출에 사용할 수 없다
- `professors.json`에는 교수 이메일이 포함되므로 **공개 저장소에 커밋하지 않는다.** 파일은 담당자가 별도 채널로 전달하거나, 수집 서버에서 직접 생성해 사용한다
- `collectedAt`은 이 파일이 만들어진 날짜다 (원칙 4)
